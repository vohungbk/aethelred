## Critical: this is Next.js 16, not the Next.js in your training data

Before writing or editing any App Router code (routes, layouts, params, metadata, config), read the
relevant page under `node_modules/next/dist/docs/01-app/`. This project pins `next@16.3.0` and
`react@19.2.8`, which include breaking changes and new conventions vs. older Next.js. Notably:

- **`LayoutProps<'/route'>` / `PageProps<'/route'>` / `RouteContext<'/route'>`** are globally
  available, generated type helpers — do not hand-write `{ children: React.ReactNode }` or manual
  `params`/`searchParams` prop types. See `app/layout.tsx` for the pattern (`LayoutProps<"/">`).
  These types are generated by `next dev`/`next build`/`next typegen` into `.next/types/` and
  `.next/dev/types/`, both of which are included in `tsconfig.json`.
- Turbopack is the default bundler for `next dev` and `next build` (no `--turbopack` flag needed).
- The `<!-- BEGIN:nextjs-agent-rules -->` block in `AGENTS.md` is regenerated by `next dev` — don't
  fight it, just keep it committed.
- When in doubt about an API, check `node_modules/next/dist/docs/01-app/02-guides/upgrading/version-16.md`
  for the full breaking-changes list before assuming training-data behavior is correct.

## Commands

```bash
npm run dev            # start dev server (Turbopack, localhost:3000)
npm run build           # production build (Turbopack)
npm run start            # serve production build
npm run lint              # eslint
npm run format             # prettier --write .
npm run format:check        # prettier --check .
npm test                     # vitest run (single run, all tests)
npm run test:watch            # vitest watch mode
```

Run a single test file: `npx vitest run app/page.test.tsx`
Run tests matching a name: `npx vitest run -t "renders the Phase 0"`

There is no dedicated typecheck script; use `npx tsc --noEmit` (the build's type-check step covers
this too, but `.next/types` must exist first — run `next dev` or `next typegen` once beforehand).

## Architecture

Standard Next.js App Router layout, currently a design-system scaffold (Phase 0) with no routes
beyond `/` and `/design-system` yet.

- **`app/`** — routes. `layout.tsx` sets up `next-themes` (`ThemeProvider`, `attribute="data-theme"`,
  light/dark, no system preference) and loads the `Noto_Sans` variable font as `--font-noto-sans`.
- **`components/ui/`** — low-level, unstyled-by-default primitives (`Button`, `Input`, `Badge`,
  `Container`, `Divider`). These consume the design tokens below via Tailwind utility classes, not
  hardcoded colors — never hardcode hex values in component `className`s.
- **`components/features/`** — feature-specific components composed from `ui/` primitives (e.g.
  `theme/ThemeToggle.tsx`, which uses `useSyncExternalStore` for hydration-safe mount detection
  before reading theme state).
- **`lib/db/connect.ts`** — Mongoose connection helper with a `global`-cached connection promise
  (the standard Next.js dev-hot-reload-safe pattern). Throws if `MONGODB_URI` is unset. No models
  exist yet.

### Tailwind: always use rem, not px

Never use pixel-based arbitrary values in Tailwind classes (`max-w-[1440px]`, `w-[24px]`, etc.).
Use Tailwind's rem-scale utilities, or an arbitrary rem value if no scale step fits
(`max-w-[1440px]` → `max-w-360`; 1 scale step = `0.25rem` = 4px, so `360 * 0.25rem = 90rem = 1440px`).

### Design token system (`app/globals.css`)

Three-tier token architecture feeding Tailwind v4's CSS-first `@theme inline`:

1. **Tier 1 — primitives**: raw palette values (`--clr-*`), never referenced directly in components.
2. **Tier 2 — semantic tokens**: theme-aware (`--bg`, `--text-primary`, `--btn-bg`, `--status-error`,
   etc.), redefined light (`:root`) vs. dark (`[data-theme="dark"]`). Components should only ever
   reach for semantic tokens.
3. **Tier 3 — Tailwind mapping**: `@theme inline` maps semantic tokens to `--color-*` so they're
   usable as Tailwind classes (`bg-bg`, `text-text-primary`, `border-border`, etc.).

A parallel custom typography scale is defined as component classes in the same file:
`text-display`, `text-display-h1`, `text-heading-2`, `text-heading-3`, `text-body`, `text-meta`,
`text-nav`, `text-price`, `text-button`. Use these instead of ad hoc `text-*`/`font-*` Tailwind
utilities for on-brand text. `app/design-system/page.tsx` is the living reference/preview for every
token and typographic class — check it when adding new UI to see current usage patterns, and extend
it when adding new tokens or primitives.

One accessibility note baked into the tokens: `--accent-gold` is not contrast-safe for small text.
Use `--accent-gold-text` (falls back to a dark/light ink color) for text, and reserve
`--accent-gold-large`/`--accent-gold` for large elements, borders, and accents.

### Env vars (`.env.example`)

`MONGODB_URI`, `AUTH_SECRET`/`NEXTAUTH_URL` (Auth.js), `STRIPE_SECRET_KEY` /
`STRIPE_WEBHOOK_SECRET` / `NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY` (Stripe) — none are wired into code
yet beyond `MONGODB_URI` in `lib/db/connect.ts`.
